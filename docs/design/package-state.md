# 订单与物流状态

## 已验证的错误来源（2026-11-04）

本人拼多多 H5 原始订单：9 条 order_status_prompt 是「拼过2次/6次」，同时 shipping_status=2、receive_time>0、combined_order_status=4；7 条旧缓存为「已提货」。旧解析只看 prompt，未识别完成后默认 stateNum=105，误列派送中。手机当前还存在一条京东「处理成功」被同样默认成 105。

## 规则

- 拼多多订单层 shipping_status=2 或 receive_time>0 是已收货证据，优先于营销 prompt；已提货/已取货/已取走/交易成功/已评价等终态也归已完成。订单状态与轨迹里的驿站代收必须区分，代收不等于用户取走。
- 未识别状态不能默认派送。只有明确派送/派件信号归派送；等待收货、已发货属于运输中。未知状态显示待更新，不伪造物流进度。
- 已确认完成的历史状态不能被营销文案或缺字段的列表响应重新变为在途。receiptConfirmed 在本地持久化，用于跨同步保留这一证据。
- 京东「处理成功」是完成处理，归已完成；未知名称不能用 105 兜底。
- 手动添加后查询无轨迹的件保留为待更新，取得物流状态后再分区。
- 手机与服务器采用同样的业务规则。升级时修正旧缓存可确认的终态；营销记录通过重新同步取得真实收货字段修复，不根据时间久远猜测签收。

## 验证

回归样例只保留合成订单字段，不能提交用户原始订单、单号、Cookie 或商品明细。须覆盖营销文案+已收货、真正运输中、驿站代收、已提货、未知状态不归派送、完成状态不回退。最终用同一真实账号重新同步并比较手机/服务器活跃分区。

## 详情与缓存（v0.9.1）

实机复现：详情轨迹已签收，但头部仍显示拼过2次和85%。原因是详情用 Intent 打开时的旧 ExpressItem，命中 PDD 缓存后不回写；旧回填还要求 latestText/latestTime 为空，营销文本或旧代收文本非空就跳过。

Store 在读取和保存时统一用已有 PDD 最新轨迹补收货证据（单次解码缓存映射），不依赖重新联网或逐件点开。详情优先读取当前 Store，取得缓存/新轨迹后通过同一 ParcelState 规则重算头部；同步完成通知已打开详情重新读取当前状态。禁止继续拿 Intent 快照渲染签收后的85%头部。驿站代收仍不认定已取走。

成功但只返回一部分的 JD/TB 列表也必须与旧记录合并，按同单号新数据优先，显式移除仍过滤隐藏表。实机JD17条仅返回8条时曾丢失9条；已从原服务器同账号历史恢复。PDD缺字段旧记录若无签收缓存，不按年龄猜测；本轮6条用已取得的真实原始 shipping_status/receive_time 证据补正。

## 待发货订单（v0.9.2）

淘宝 bought-list 中 WAIT_SELLER_SEND_GOODS/买家已付款还没有 SSR 运单；不能仅保存 SSR 物流页。以独立订单键保存 orderOnly=true，展示订单号、商品和待发货，不显示运输百分比、不查虚构单号的轨迹。获得正式运单后按 source/accountId/queryChannel 匹配替换，保留跟踪/地址等用户设置；部分列表不删除未出现的历史，明确交易关闭/待付款才撤掉旧待发货记录。

拼多多最新第一页由 window.rawData.ordersStore.initOdersList 注入 HTML，后续 XHR 常从第二页开始；只抓网络响应会漏掉最新商品。读 initOdersList 的原始完整订单，不使用 orders/currentList 中缺状态的摘要模型；继续读取待发货、待收货分类与全部分页。真实新订单 shipping_status=0、pay_status=2、receive_time=0，prompt=拼单成功，待发货，与旧签收字段区分。

正式版不接受 skip_channels 验收参数；返回主页时按 60 秒限流触发同步。同步进行时不另启动 PDD 历史轨迹补抓，避免先查旧件拖延新订单列表。

普通手机刷新使用最新列表模式：淘宝第一页、京东/PDD首批，WebView最迟15秒收尾；完整翻页仅维护API includeHistory=true。京东明确转登录验证页立即返回错误并保留旧数据，不在首页等60秒；PDD已完成件不再每次刷新补抓轨迹，详情仍按需读取。重复下拉在已有同步时提示正在刷新，不排队多个全量任务。
